## 1. Executive Summary & Purpose

This document constitutes the **formal contract** between the Product Requirements Document (PRD) of **Railway Network Manager — Indonesia** and the **AI Engineering Assistant (Model)**. It establishes:

1. **The AI Operational & Governance Contract**: Strict behavioral, scoping, decision-making, and verification protocols governing how the AI model ingests requirements, writes code, maintains invariants, and enforces boundaries.
2. **The Railway Simulation Domain Model**: The complete, bounded-context domain architecture comprising all entities, value objects, aggregates, state machines, and mathematical contracts required to simulate an Indonesian passenger and freight railway operator.

This document serves as the **immutable primary reference** for all subsequent implementation phases (Phase 1 through Phase 7). Any code generated by AI must adhere to the types, contracts, invariants, and boundaries defined herein.

### 2.1 The Source-of-Truth Hierarchy Contract (PRD §41)

When discrepancies arise between documents, schemas, or implementations, the following precedence order is absolute:

$$\text{PRODUCT\_PRD} \succ \text{GAME\_DESIGN} \succ \text{DOMAIN\_MODEL} \succ \text{SIMULATION\_RULES} \succ \text{API\_SPEC} \succ \text{IMPLEMENTATION}$$

* **Rule 2.1.1 (Downstream Subservience):** Implementation code must never override, loosen, or silently redefine domain rules or PRD requirements.
* **Rule 2.1.2 (Conflict Escalation):** If code generation reveals a logical contradiction between upstream specifications, the AI **must halt** and request clarification. It must never fabricate an unapproved resolution.

### 2.2 The Six Invariant AI Coding Laws (PRD §37)

The AI model operates under six non-negotiable operational invariants:

| Law | Principle | Description & Guardrail |
| :--- | :--- | :--- |
| **Law 1** | **Bounded Scope Only** | Never attempt to build the entire system in a single step. All tasks must target an isolated module or bounded context (e.g., `packages/procurement`). |
| **Law 2** | **Read Docs First** | Before writing code, the AI must inspect existing documentation (`PRODUCT_PRD.md`, `DOMAIN_MODEL.md`, `SIMULATION_RULES.md`, `API_SPEC.md`). |
| **Law 3** | **Minimal Blast Radius** | Changes must be confined to the minimal necessary files. Gratuitous refactoring of unrelated modules is strictly prohibited. |
| **Law 4** | **Zero Game Rule Invention** | If a business logic rule, formula, or constraint is missing or ambiguous: **STOP** $\rightarrow$ identify ambiguity $\rightarrow$ propose explicit options $\rightarrow$ await player/user approval. |
| **Law 5** | **Tests Before Refactoring** | Every simulation rule, state transition, and invariant must be accompanied by deterministic unit tests (Vitest) before refactoring. |
| **Law 6** | **Balance Lives in Data** | Numerical constants, tariffs, speeds, and probabilities must reside in configurable game data (`packages/game-data`), never hardcoded in logic. |

## 4. Core Simulation Engine Contract (PRD §34, §35)

### 4.1 Deterministic Tick Contract

The engine executes as a pure state transition function:

$$\mathcal{S}_{t+1} = \text{simulateTick}(\mathcal{S}_t, \mathcal{A}_t, \mathcal{C}, \sigma)$$

```typescript
export interface SimulationEngineContract {
  simulateTick(
    currentState: Readonly<GameState>,
    playerActions: ReadonlyArray<PlayerAction>,
    config: Readonly<GameConfig>,
    seed: number
  ): SimulationResult;
}

export interface SimulationResult {
  readonly nextState: GameState;
  readonly emittedEvents: ReadonlyArray<SimulationEvent>;
  readonly metrics: TickExecutionMetrics;
}
```

* **Determinism Invariant:** For any given tuple $(\mathcal{S}_t, \mathcal{A}_t, \mathcal{C}, \sigma)$, the output $\mathcal{S}_{t+1}$ and emitted events must be bit-for-bit identical across Node.js, Web V8, and Hermes runtimes.
* **PRNG Invariant:** Native `Math.random()` is strictly prohibited in `packages/simulation`. A deterministic seeded PRNG (e.g., Mulberry32 or Xoshiro128) parameterized by $\sigma$ must be used for all stochastic evaluations (delays, component wear).

#### 5.6.2 Passenger Demand Formula Contract
Demand between origin station $A$ and destination station $B$ for class $C$ during tick interval $T$ is computed deterministically:

$$\text{Demand}_{A,B,C} = \text{BaseDemand}_{A,B} \times \text{TimeFactor}(T) \times \mathcal{E}(\text{Fare}_C, \text{BaseFare}_C) \times \mathcal{F}(\text{Frequency}) \times \mathcal{Q}(\text{ServiceQuality}) \times \mathcal{R}(\text{Reputation})$$

* **Load Factor Contract:**
  $$\text{LoadFactor} = \frac{\text{Passengers Served}}{\text{Available Capacity}}$$
* **Overcrowding Invariant:** A Load Factor $> 100\%$ on unreserved services degrades customer satisfaction and increases dwell time:
  $$\text{DwellPenalty} = \max(0, \text{LoadFactor} - 1.0) \times \text{DwellPenaltyFactor}$$

### 5.8 Workforce & Workload Domain (PRD §12)
